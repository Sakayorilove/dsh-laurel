# 系统层问题与提示词

**这份文件回答一个问题：护栏治不了的那些坑，怎么办。**

护栏只能约束「协作方式」。有一类问题它在插件层**绕不过去**，也不该去绕 —— 权限、网络、路径、宿主配置。绕过去的代价是把沙箱拆了。

所以这些一律**在本机就地解决**，然后把解决过程和「怎么让 AI 帮你做」固化成下面这份东西。

用法：**每一条都可以整段复制给 AI。** 提示词都写成自包含的（不依赖当前对话），所以在新会话里也能直接用。

## ① 沙箱权限被挡

**症状**

```
cannot read <路径>
cannot modify <路径>
cannot write <路径>
cannot edit <路径>
```

实测一天里出现 `cannot read` 11 次、`cannot modify` 11 次、`cannot write` 3 次、`cannot edit` 3 次。

**根因**

不是你代码写错了，是**沙箱档位**或者目录 ACL 挡住了。常见的两种情形：

1. 沙箱档位是「Workspace Write」——只允许写工作目录之内，工作目录之外一律拒。
2. 目标目录属于管理员或另一个用户，当前账户没有写权限。

**就地解决**

第一步：确认当前档位。

- 看 Harness 的权限/沙箱设置里当前是哪一档（Workspace Write / Full access）。
- 不要为了省事直接开 Full access —— 那是把整个机器敞开。

第二步：**对固定工作目录预先授权**，而不是整个盘一刀切。

- 把「我确实需要读写」的那几个目录列出来（例如 `D:\<WORKSPACE>\...`、`C:\Users\<你>\projects`）。
- 让它们落在工作目录之内，或者单独授权这几个目录。

第三步：如果目录属于管理员，改所有权（**需要管理员权限的终端**）：

```powershell
# 把目标目录的所有权收到当前用户
takeown /F "D:\你的目录" /R /D Y
# 给当前用户完全控制
icacls "D:\你的目录" /grant "%USERNAME%:(OI)(CI)F" /T
```

**验证**

```powershell
# 应该能列出内容
Get-ChildItem "D:\你的目录" | Select-Object -First 3
# 应该能写进去（用完删掉）
"test" | Out-File "D:\你的目录\.write-test" ; Remove-Item "D:\你的目录\.write-test"
```

**给 AI 的提示词**

```text
我在 DeepSeek Harness 里操作文件时反复遇到这些报错：
  cannot read / cannot modify / cannot write / cannot edit <路径>

请按下面的顺序帮我查，每步都把命令和输出给我看：
1. 确认 Harness 当前的沙箱/权限档位是哪一档（Workspace Write 还是 Full access），
   以及当前的工作目录是什么。不要建议我直接开 Full access。
2. 用 icacls 看目标目录的 ACL，指出当前用户缺哪一项权限。
3. 给出**最小范围**的修复方案：只授权我真正需要读写的那几个目录，
   不要对整个盘或整个用户目录授权。
4. 如果要改所有权，把需要管理员权限的命令单独列出来，并说明每条命令做什么。

约束：
- 不要对整个盘（C:\ / D:\）做任何授权或所有权变更。
- 不要删除任何文件。改完只做「能读 / 能写」的验证。
- 每一步之前先说明它会不会改变现有权限，改了什么。
```

## ② 改目录 ACL 失败（Win32 5）

**症状**

```
SetNamedSecurityInfoW failed (Win32 5)
```

（Win32 错误码 5 = `ERROR_ACCESS_DENIED`）

**根因**

改目录的访问控制列表（ACL）需要 `WRITE_DAC` 权限，而普通用户对不属于自己的目录没有这个权限。**这不是 bug，是设计。**

**就地解决**

两条路，按顺序试：

**路 A：用管理员权限改一次（推荐）**

1. 开始菜单搜 `PowerShell` → 右键 → **以管理员身份运行**。
2. 跑 `①` 里那两条 `takeown` / `icacls`。
3. 改完之后，日常操作**不需要**再开管理员 —— 权限已经落在目录的 ACL 上了。

**路 B：把工作目录挪到已有写权限的位置**

如果这个目录本来就不该归你（比如是别的软件的安装目录），别去改它，换个地方：

- 工作目录放到 `C:\Users\<你>\` 下面，或者你的项目盘。
- 只有**必须**原地改的时候才走「路 A」。

**验证**

```powershell
# 看 ACL 里有没有你的用户名 + 完全控制
icacls "D:\你的目录"
```

**给 AI 的提示词**

```text
我在 Windows 上改目录权限时报 SetNamedSecurityInfoW failed (Win32 5)，
也就是 ERROR_ACCESS_DENIED。

请帮我判断：
1. 这个目录当前的 owner 是谁、ACL 里有没有我的账户（用 icacls 和 Get-Acl 查）。
2. 这个目录是不是系统目录 / 别的软件的安装目录？
   - 如果是，告诉我"不该改它"，并给我一个替代的工作目录方案。
   - 如果不是，给我**最小权限**的修复命令（takeown + icacls），
     并明确标出哪几条需要管理员权限。
3. 改完之后怎么验证（一条只读命令）。

不要：
- 对整个盘或整个用户目录改 ACL。
- 加 Everyone 的权限。
- 用 /grant 给超出需要的权限（比如不需要就别说 F 完全控制，说 M 修改）。
```

## ③ WSL 文件走 UNC 路径（又慢又被反复读）

**症状**

- 读一个文件特别慢。
- 同一个文件在一个会话里被读 **60 次**（另两个 56 / 31 次）。
- 路径长这样：`\\wsl.localhost\Ubuntu-26.04\home\...`

**根因**

两个问题叠在一起：

1. **跨 UNC 路径访问本身就是慢的** —— 每次读写都要过一次 9P 协议栈。文件越大、调用越频繁，越明显。
2. **慢 → 上下文里没留住 → 反复读**。这不是模型的错，是路径选错了。

**就地解决**

**不要跨 `\\wsl.localhost` 干活。** 让 bash 与文件读写**都跑在 WSL 发行版内**：

```bash
# 在 WSL 里（不是 Windows 侧）：
# 项目放在 WSL 的原生文件系统里，不要放 /mnt/c
mkdir -p ~/projects
cd ~/projects

# 确认你现在的路径不是 /mnt/...
pwd     # 期望：/home/<你>/projects/...
```

从 Windows 侧要用 WSL 里的东西时，**用 WSL 命令去操作**，而不是用 Windows 路径去读：

```powershell
# ✓ 对：让 WSL 自己执行
wsl.exe -d Ubuntu-26.04 -u <你> -- bash -lc 'ls ~/projects'

# ✗ 错：跨 UNC 路径直接读
Get-ChildItem "\\wsl.localhost\Ubuntu-26.04\home\<你>\projects"
```

**这条和护栏的关系**：护栏的「重复读提醒」会在读同一个文件第 3 次时提醒你。**但真正的修法是换路径** —— 提醒只是让问题暴露出来。

**验证**

```bash
# 在 WSL 里跑，看耗时
time ls -R ~/projects > /dev/null
```

对比一下同样的事走 UNC 路径要多久。

**给 AI 的提示词**

```text
我在 Windows 上用 DeepSeek Harness 干活，项目文件在 WSL 里。
我怀疑我一直在跨 \\wsl.localhost\... 这样的 UNC 路径读写 WSL 文件，导致：
- 读文件很慢
- 同一个文件在一个会话里被反复读了几十次

请帮我：
1. 检查我的项目到底放在哪：
   - 在 WSL 里跑 `pwd`，看是不是 /mnt/c 或 /mnt/d 下面（那样就是反的，应该放 ~/projects）。
   - 在 Windows 侧看我是不是在用 \\wsl.localhost 或 \\wsl$ 路径操作。
2. 如果项目在 /mnt/c 或 /mnt/d 下面：告诉我怎么迁到 WSL 原生文件系统（~/projects），
   并给出迁移命令（用 rsync 或 cp -a，保留权限）。
   ⚠ 迁移前先确认目标目录不存在同名内容；不要用 mv 跨文件系统，慢且容易中断。
3. 给我一份"正确的调用方式"对照：哪些操作该在 WSL 里跑，
   哪些该在 Windows 侧跑，以及从 Windows 侧要操作 WSL 文件时该用什么命令。

约束：
- 不要删任何文件。迁移是"复制 + 你确认后再删原目录"两步。
- 不要改我的 WSL 发行版配置。
```

## ④ 抓文档被跨域跳转挡住

**症状**

```
cross-origin redirect
```

抓 `claude.com` / `platform.claude.com` / `developers.openai.com` 时出现，实测一天 5 次。

**根因**

裸 `fetch` 默认**不跟随跨域跳转**。这些站点会先跳到另一个域名（例如 `claude.com` → `platform.claude.com`），裸 fetch 到跳转那一步就停了。

**就地解决**

用**能跟随跳转的抓取通道**，别用裸 fetch：

1. **搜索桥** —— 用搜索工具拿到内容，而不是直接抓 URL。搜索工具通常已经在服务端处理过跳转与反爬。
2. **浏览器** —— 需要看真实渲染结果时，用能驱动真实浏览器的通道（CDP 那一类），而不是 HTTP 抓取。
3. **系统代理层放行** —— 如果你有代理软件，确认它没有把跳转链上的域名拦掉。

**给 AI 的提示词**

```text
我抓 https://claude.com/... 或 https://platform.claude.com/... 或
https://developers.openai.com/... 的时候报 cross-origin redirect。

请帮我：
1. 先用 `curl -sIL <URL>` 把完整的跳转链打出来（每一跳的 status + location），
   告诉我它从哪个域跳到哪个域。
2. 判断跳转是不是"同站不同子域"（那通常只是规范化）还是"真的换了域"。
3. 给我两套可用的取内容方案，并说明各自的取舍：
   a) 用搜索工具拿内容（服务端已经处理过跳转）
   b) 用能跟随跳转的抓取（带 --location 的 curl / 或浏览器通道）
4. 不要用裸 fetch 的方案 —— 它不跟随跨域跳转，这正是问题本身。

约束：只做只读抓取，不要提交任何表单、不要登录。
```

## ⑤ 搜索没有 key

**症状**

```
DeepSeek search has no API key
```

实测一天白试 5 次。

**根因**

搜索插件缺凭据。**它不会自动降级到免费引擎**，所以你只能看着它一次次失败。

**就地解决**

两条路：

1. **补 key** —— 在搜索插件的设置页填上 API key。这是最直接的。
2. **配一个免费引擎回退** —— 如果你不想为搜索付费，用支持免费引擎（DuckDuckGo / Bing / SearXNG）的搜索方案，让它在没有 key 时自动走免费通道。

**给 AI 的提示词**

```text
我的 DeepSeek Harness 里搜索一直报 "DeepSeek search has no API key"。
我现在没有付费搜索的 key，也不想买。

请帮我：
1. 找出是哪个插件/配置项在要这个 key（看 Harness 的插件列表和它读的配置键名）。
2. 给我两个方案，并说明各自要不要花钱、要不要联网注册：
   a) 有免费额度的搜索 API（列出 2-3 个，说明免费额度是多少、怎么申请）
   b) 完全免费的引擎回退（DuckDuckGo / SearXNG 自建），
      以及怎么让搜索工具在"没有 key"时自动走这条路
3. 只读地检查我现在的配置里跟搜索有关的项，告诉我缺哪一项。

约束：不要改我其它插件的配置。给出改动前后的对照。
```

## ⑥ 上下文压缩一次都没触发

**症状**

- 上下文单步中位 **218k**、峰值 **627k**（健康值 40–80k）。
- **全程零压缩** —— 一次都没触发过。

**根因（两种，先查第一种）**

**第一种：压缩件被禁用了。** 这是实测踩到的那一种，也最容易被漏掉。

有些上下文类插件（例如 `billion-context`）和宿主内置的压缩**是互斥关系**，它们的 README 会让你
**先禁掉** `compaction-basic` / `tool-result-pruner` 再装。等你后来把那个插件卸掉，
**禁用状态会留在基础层** —— 于是变成「两边的压缩都没有」，而且界面上什么都看不出来。

查法（只读，先看再改）：

```powershell
Select-String -Path "$env:USERPROFILE\.dsh\profiles\desktop\cordis.yml" `
  -Pattern "compaction-basic|tool-result-pruner" -Context 0,3
```

看到 `disabled: true` 就是它。

**第二种：阈值够不着。** 内置压缩的默认触发点是
`floor(min(W × thresholdRatio, W − O − 65536))`，默认 `thresholdRatio: 0.8` ——
1M 窗口约等于 **80 万 token** 才动手，长会话常常到不了就结束了。

**这是插件避不开的一类**：护栏能做的是「每长大一段就提醒一次」（`waterLevelStep`）和「按条数微压缩」（`microCompact`），但**改不了宿主自己的阈值、也开不了被禁用的件**。

**就地解决**

在 profile 的 `cordis.patch.yml`（用户层）里**恢复启用** + 调紧阈值：

```yaml
- id: compaction-basic
  disabled: false          # ← 关键的一句：基础层禁用了，只调阈值没用
  config:
    thresholdRatio: 0.3    # 原 0.8：30 万 token 就压，别等 80 万

- id: tool-result-pruner
  disabled: false
  config:
    thresholdChars: 8192   # 单条工具结果超过就裁掉中段
    headChars: 4096
    tailChars: 1024
```

> 键名以你机器上实际的 profile 配置为准 —— 先读一遍 profile 的 `cordis.patch.yml` 和 `cordis.yml`
> 确认这两个 id 存不存在、`disabled` 现在是什么，再改。
> ⚠ 这两个 id 在 patch 里**只能有一行** —— 加之前先 grep 一遍，同 id 两行会让 loader 报重复条目。

**验证**

改完**完全退出** Harness 再打开（改的是用户层，重启才读），跑一个长会话，
看 `~/.dsh/` 下的会话日志里有没有压缩事件。

**给 AI 的提示词**

```text
我的 DeepSeek Harness 长会话里上下文只涨不降（单步中位 218k、峰值 627k token），
宿主的自动压缩一次都没触发过。我怀疑有两种可能，但不确定是哪种：
  (a) 压缩件被禁用了 —— 我以前装过别的上下文插件，它的 README 让我先禁掉内置压缩，
      后来插件卸了，禁用状态可能留下来了；
  (b) 阈值够不着 —— 默认是窗口的 80%，1M 窗口 = 80 万 token，我根本到不了。

请帮我：
1. **先判断是 (a) 还是 (b)** —— 只读地找出我 profile 里的配置文件（通常是 profile 目录下的
   cordis.yml 与 cordis.patch.yml），把跟下面两件事有关的行原样打给我看，
   **特别要指出每个 id 的 disabled 现在是什么值**：
   - 工具结果裁剪（关键词：pruner / thresholdChars / headChars / tailChars）
   - 自动压缩（关键词：compaction / thresholdRatio）
2. 告诉我这两行现在**实际生效的值**是多少（patch 层可能覆盖了基础层，
   用户层又可能覆盖了 patch 层 —— 把三层都看一遍，说清谁盖了谁）。
3. 给我一份最小改动：
   - 如果是 (a)：在 profile 的 cordis.patch.yml 里把这两个 id 恢复成 `disabled: false`
     （⚠ patch 里同一个 id 只能有一行，加之前先 grep 确认没有重复）。
   - 如果是 (b)：把阈值调紧到"长会话能真的触发一次"的程度。
   两种情况都要说明改了之后有什么副作用（比如压缩太频繁会不会丢信息）。
4. 改完告诉我怎么验证它真的生效了（看哪个日志、找什么关键字）。

约束：
- 先读后写。把改动前后的对照打出来再动手。
- 不要动 profile 里跟我这个问题无关的行。
- 用户层的 cordis.patch.yml 里已经有的行不要重复加。
```

## ⑦ 工具硬超时 30 秒

**症状**

```
tool call timed out after 30000ms
```

**根因**

宿主的 `dsh-tool-call-timeout-policy` 只对「**自己声明了 `timeoutMs` 的工具**」生效。声明了的工具被套上硬超时，没声明的就不管 —— 所以表现是「有的工具 30 秒就被掐、有的能跑一小时」。

**就地解决**

两种：

1. **给长任务工具声明更长的 `timeoutMs`** —— 治本，但要改工具定义。
2. **超过 30 秒的一律丢后台跑** —— 立刻能做。把长命令写成后台任务，然后用「查输出」的方式取结果，而不是阻塞等。

> 注意：护栏给 `wait_agent` 压等待上限（`waitCapMs`）解决的是**另一个**问题 —— 那是「等太久」，这是「被掐太早」。两者不冲突。

**给 AI 的提示词**

```text
我在 DeepSeek Harness 里跑长任务时报 tool call timed out after 30000ms。

请帮我：
1. 找出是哪个工具在 30 秒被掐断的（看会话日志里超时那条的前一条 tool/call）。
2. 判断它是不是"本来就该跑超过 30 秒"的任务：
   - 如果是：告诉我怎么给它声明更长的 timeoutMs（在工具定义里加，不是全局放开）。
   - 如果不是：说明它为什么慢，有没有更快的等价做法。
3. 不管哪种情况，都给我一个"把长任务丢后台、然后用非阻塞方式取输出"的改法，
   并说明后台任务失败时怎么知道它失败了。

约束：
- 不要全局放开超时。逐个工具处理。
- 后台任务必须能看出成功还是失败，不许"启动完就不管了"。
```

## ⑧ 子代理层级上限（别放开）

**症状**

```
subagent depth 2 exceeds maxDepth 1
```

**根因**

子代理想再开子代理，被层级上限挡住。**这是保护机制，不是 bug。**

**就地解决**

**不要放开 `maxDepth`。** 改成让子代理**把子任务回给父级**，由父级决定要不要展开。

理由（Anthropic 多智能体研究的结论）：层级越深，越难追踪「这个结论是谁得出的、基于哪一版数据」，而且每一层转述都会失真。护栏的星型拓扑规则就是为这个加的 —— 子代理只对主控汇报，不要自己再拉一层。

**给 AI 的提示词**

```text
我的子代理报 subagent depth 2 exceeds maxDepth 1。
我知道这是保护机制，我不打算放开 maxDepth。

请帮我改掉"子代理自己再开子代理"这个做法：
1. 找出在哪个环节它想开子代理（看会话日志里报错那条的上下文）。
2. 把它改成：子代理把"我需要再做 X 件事"回给主控，
   由主控决定是自己做、还是另开一个平级子代理。
3. 顺便帮我写一段可以放进系统提示词的规则，明确写清：
   - 子代理不要自己开子代理
   - 子代理只向主控汇报，不要直接联系其他子代理
   - 派活时必须写清目标、输出格式、边界（哪些不做）

约束：不要改 maxDepth 的值。
```

## ⑨ 队友正忙

**症状**

```
active teammate
```

给还在干活的子代理发消息或派活时报这个。实测一天 2 次。

**根因**

目标子代理还在忙。**它不是"坏了"，是"没空"。**

**就地解决**

两条：

1. **发消息前先查状态** —— 别盲发。
2. **把「忙」变成「排队」而不是报错** —— 但排队要小心：它会让上游一起卡住。更省时间的做法是**先做不依赖它的部分**。

**给 AI 的提示词**

```text
我给子代理发消息/派活时报 active teammate（它正忙）。

请帮我：
1. 改成"先查状态再发"：在派活/发消息之前先看目标子代理的状态，
   忙的话不要盲发。
2. 给我一个更好的默认做法：当目标忙时，
   - 优先做当前不依赖它的部分（把依赖项列出来，先做能做的）
   - 而不是原地等待或反复重试
3. 如果确实必须等，给我一个带超时的等待方式（不要无限等），
   并说明超时之后该怎么办。

约束：不要改成无限重试。不要为了提高并发而放宽任何超时。
```

## 三、和护栏的分工

| 这一层 | 谁管 |
|---|---|
| 协作方式（等待上限、串扰、返工、上下文水位、共享资源） | **护栏**（这个插件） |
| 权限、ACL、路径、网络、凭据 | **本机就地解决**（这份文件） |
| 宿主自己的阈值（pruner / compaction / timeoutMs） | **profile 配置**（这份文件的 ⑥⑦） |
| 设计边界（maxDepth） | **不改**（这份文件的 ⑧） |

护栏的价值在于：**它把「本机问题」暴露出来**。比如重复读提醒响了，说明你在跨 UNC 路径读 WSL 文件 —— 提醒本身不解决问题，但它让你**看得见**问题。看见之后就来这份文件里找对应的那一条。
